# Lancer workbench in Pi Web

The Lancer workbench is embedded into the existing Pi Web conversation. Its source is adapted from `raylee-ai/lancer` commit `4dd8fe7134cd663a85f9a815ad90bb2685760da9`; the SVG light renderer and its MIT attribution live in `lib/vendor/lancer-light-ui`.

## Using it

Open a saved conversation or a fresh composer with a project selected. The row above the conversation provides a module selector and **Manage modules**; saved conversations also provide **Task tree**.

For a fresh composer, selecting a module copies its template locally. Configure its stages, select a model and load a task before sending. Selection and editing do not create an AgentSession. On the first send, the real session is ensured, the exact workflow snapshot is saved, and only then is the prompt dispatched. A save conflict or archived module rejects the send and keeps the submitted draft recoverable. Selecting a project/worktree carries the workflow with the composer; another independent fresh composer starts with its own choice. The plan and selected stage survive a tab reload. Chat text and attachments keep Pi Web's existing page-memory draft behavior; use **Load task** again to regenerate a stage prompt after reload.

- **Task tree** opens a docked event tree beside the conversation. On phones it opens over the conversation and has an explicit close button. Choose the current conversation, its subtask family, or the project. Read failures are isolated to a lane, with Retry. The existing full session map remains available.
- Nodes link to recorded conversation entries. Clicking an entry on the active branch scrolls to it; selecting an inactive branch uses the existing guarded tree-navigation operation. Fork uses the same guarded operation as the session map. A running conversation keeps its existing navigation restrictions.
- **Deliverables** lists files from successful coding-tool write/edit/patch results. The server checks that a file still exists inside its conversation's checkout. Opening it uses the existing file viewer and file access rules. A mentioned filename alone is not a delivery record.
- Choose a module to copy its stage template to this conversation. **Configure stages** edits this conversation's copy; **Manage modules** edits reusable templates. Template edits do not overwrite existing conversation plans. Archive and restore modules without deleting their conversation histories. Switching to ordinary chat retains the last workflow for restoration.
- Each of 1–8 stages has a title, model, selected skills, goal and deliverables. Select a stage to switch the actual model of the current Pi session. A rejected switch does not select the stage. **Load task** fills an empty composer for review; it never sends a prompt. Existing text and attachments are preserved and block loading.
- Stage selection is not task completion. Automatic stage execution and Git code merging are separate future features.
- New message, model and delivery events emit Lancer's 1.2-second lights from their exact visible model selector and message bubble to their native tree-node dot. Each session keeps a color shared by its flights, nodes and relationship lines. Raw tool rows and loaded history are silent. The tree may follow new nodes in its own scroller; the chat is never scrolled by a flight. Executing assistant bubbles and phase rows have the original narrow running border. Closing the tree destroys its light layer, hidden pages pause motion, and reduced-motion retains results without flight or border animation. A fresh opening snapshot establishes a silent baseline; normal refreshes retain existing node DOM, scroll and focus. Canonical message IDs may arrive after the graph: each source is tracked separately in a bounded queue (64 events, up to 15 seconds), without replaying an already emitted source. Missing, clipped or expired anchors are omitted rather than replaced with nearby elements; clipping is rechecked during each flight.

## Reviewing results and recorded changes

The task tree now includes **Task relationships**: solid lines show recorded delegation, dashed lines show a result returning to a parent. Click a relationship endpoint to inspect its native transcript entry. An accepted result makes its return line stronger. Missing or ambiguous relationships are omitted; similar session titles do not create a link.

For a returned subtask report, choose **Pending review** to read the result and its available delivered files. **Mark reviewed** binds your decision to that exact native result and current file contents. You can then **Accept result**, or enter a reason and choose **Request changes** or **Reject result**. These are manual review records: they do not dispatch another model request, copy files or merge Git branches. Decisions survive reload. Refreshing the graph keeps the open review and its notes; switching the conversation or tree scope closes it, and a delayed response from the previous scope does not reopen it. If the child resumes, the report changes or a delivered file changes, the prior decision becomes stale and needs a new review. Failed, missing, oversized or unverifiable results cannot be accepted. Older reports without a native result-entry identity remain visible but are unavailable for acceptance.

**Turn changes** records future agent activity only after you enable **Record future runs** for that saved session. Select a finished run and a changed file to read its before/after contents. **Mark file reviewed** saves a mark for that immutable snapshot/file; it does not mean a newer version of the file has been reviewed. Stop and interrupted runs, truncated responses, skipped binary/oversized files and overlapping recordings have explicit coverage states. A comparison includes checkout changes between its two boundaries; external edits and concurrent tasks can be included, so it is not exclusive attribution to an agent.

Recording uses Git only to read checkout identity and inventory. It does not stage, unstage, commit or change source refs. Opt-in on a runtime opened before the recorder was installed returns a visible message to reopen/reload the idle session first. The snapshot system records one settled activity including automatic retries and continuations, not a separate image for every tool call. Newly created built-in subagents carry the same recorder, but recording remains opt-in for each saved child session; it is not inherited from the parent. Enabling a child's recorder after its first run records subsequent resumes without reopening its runtime.

## Storage and compatibility

Modules, per-session workflows and manual subtask result decisions are auxiliary UI data in `<pi agent directory>/pi-web-workbench.json`. Writes use a revision, a per-process queue, a cross-process lock and an atomic file replacement. A concurrent stale save is rejected, and invalid existing bytes are preserved. This does not rewrite Pi session history, credentials or model settings. Browser tab state remembers whether the tree is open.

The task graph observes existing runtimes or cached read-only session managers; it does not start model sessions. Snapshots are kept in `<pi agent directory>/pi-web-turn-snapshots-v1`, with independent compressed contents and bounded retention (50 finalized runs per session, 500 overall; open records are not pruned). File review marks are in `pi-web-snapshot-reviews.json`, bounded to 5,000 recent marks. Captures currently handle UTF-8 text files up to 512 KiB, at most 2,000 files / 8 MiB per boundary and a 3-second capture budget, with a 2 MiB detail response cap. Checkout discovery uses the same 3-second cutoff rather than a shorter preflight timeout. Within each capture boundary, checkout validation and the two read-only inventories run concurrently under one deadline; inventory output shares a 1 MiB byte cap, and a failed or cancelled query cancels its siblings and waits for their processes to close before returning. File contents are read only after all three queries succeed and the checkout identity matches. Omitted contents are never presented as deleted files. Each new manifest also records bounded ignored-path metadata without reading ignored contents: a change to ignore rules is not reported as a file creation or deletion. Older manifests that lack this metadata cannot infer an untracked file's absent contents. Legacy session formats are shown as unavailable for graph/review operations rather than invoking the SDK's history migration. Source worktrees may be removed later; recorded contents remain available while their owning saved session and retained snapshot remain readable.

Task graph reads and rendering are bounded (40 lanes, 300 nodes per lane, 1,200 nodes overall; disk sessions above 16 MiB have an explicit unavailable lane). Internal subagent relations are supported. Third-party orchestration tools need their own data adapter to provide equivalent task status and return edges.

The embedded feature uses the existing Pi engine, model catalog, Skills, MCP, authentication, file viewer, personalization and completion sounds. No Magpie, Electron runtime or second model gateway was added.

## Verification

`node --experimental-strip-types --test --test-force-exit lib/workbench/workbench.test.mjs` tests validation, template isolation, concurrent writes, corrupt-file retention, task families, native graph edges and delivery evidence.

`node e2e/lancer-workbench.mjs` runs the actual page in Edge with isolated HTTP fixtures. It tests task-tree rendering, model handoff, draft protection, loading without sending, workflow saves, light emission and cleanup, and a 390px layout. It does not contact a model provider or establish cross-provider conversation compatibility.

`node e2e/lancer-new-session.mjs` verifies fresh-composer selection, local stage edits, plan/model restoration after reload, and the exact ensure → save workflow → first prompt order with isolated HTTP fixtures.

Real provider acceptance is explicit: `LANCER_RUN_LIVE=1 node e2e/lancer-live-handoff.mjs` verifies context across two model choices through the running Pi Web HTTP API. `LANCER_RUN_LIVE=1 node e2e/lancer-live-subagents.mjs` uses an isolated agent directory, the existing subagent controller and configured credentials for two concurrent child runs, report delivery, Stop and resume. Optional `LANCER_LIVE_MODELS` selects the two `{provider, modelId}` records as a JSON array; the default acceptance pair is `ppt/gpt-6.1-sol` and `ppt/gpt-6-astra`. These commands make actual model requests and save clearly named acceptance evidence. `node e2e/lancer-reopen-results.mjs` then checks their persisted records in a fresh process without making a model request. Provider-specific thinking values and gateway availability still determine whether a selected acceptance pair can run.

Native subagent reports are projected from SDK `custom_message` entries with type `pi-web:subagent-notification`; they are not inferred from response prose.

`node e2e/lancer-result-review.mjs` verifies the review/accept/change-request flow, stale rejection, explicit delegation/return connections, opt-in snapshot controls, before/after viewing, persistent file marks and a narrow viewport using isolated HTTP fixtures. It also holds graph and save responses to verify review continuity and scope-change isolation. `LANCER_RUN_LIVE=1 node e2e/lancer-live-capture.mjs` opts in a temporary checkout, checks actual model-written before/after files and review persistence, and verifies that HEAD and index remain unchanged.

`lib/workbench/turn-snapshot-capture-budget.test.mjs` deterministically checks concurrent query startup, checkout validation before content reads, aggregate inventory limits and sibling cancellation without depending on host process-launch speed.

`lib/subagent-turn-snapshot.integration.test.mjs` exercises a newly spawned child and two recorded resumes through the real SDK with a faux provider, without an RPC reopen. Unit/API/SDK capture tests are in `lib/workbench/*test.mjs` and `app/api/workbench/snapshots/route.test.mjs`; they verify that baselines finish before tools, final capture precedes settled notification, source staging remains unchanged, ownership and request validation hold, and interrupted or partial captures stay explicit.

### Light UI fidelity checks

`node e2e/lancer-light-preview.mjs` starts an isolated UI-only host on port 30143 (or reuses that verified fixture). It renders the actual Pi Web components with no provider API routes; it does not replace the production server. Open `/motion-fixture` for the interactive light fixture and `/graph-motion` for the remote-graph/canonical-ID fixture.

`node e2e/lancer-light-fidelity.mjs` checks dual sources, exact node-dot landing, per-session colors, the original 1200ms timing, running borders, burst limits, independent tree scrolling, cleanup and reduced motion. `node e2e/lancer-light-lifecycle.mjs` separately checks request coalescing, preserved tree DOM/scroll/focus, delayed canonical IDs, clipping during a flight and silent reopening/visibility recovery. The tests use HTTP/DOM fixtures and send no model requests. Optional `LANCER_UPSTREAM_BASE` runs the original Light UI browser lifecycle page for comparison. Source tests are `hooks/task-light-anchors.test.mjs` and `hooks/useTaskGraph.test.mjs`.

The later plan milestones—automatic workflow execution, scheduling, video processing and macOS desktop control—remain separate from the embedded workbench. Full Git staging/branch-review controls and automatic code merging are not provided by the result-acceptance action.
